# 가맹점 검색·매핑 전체 검토 (2026-08-29)

인입내역 등록 시 "가맹점 검색이 안 되고, 이름을 입력해도 기존 가맹점에 매핑되지 않는다"는
보고를 받고, 가맹점을 검색·연결하는 경로 전체를 검토한 기록.

## 검토 범위

| #   | 위치                                                    | 용도                                    |
| --- | ------------------------------------------------------- | --------------------------------------- |
| 1   | `tickets/new/NewTicketForm.tsx`                         | 인입내역 등록 폼의 가맹점 자동완성·연결 |
| 2   | `tickets/page.tsx` + `TicketsClient.tsx`                | 인입내역 목록의 가맹점명·제목·기사 검색 |
| 3   | `merchants/page.tsx`                                    | 가맹점 360 검색 (비교 기준)             |
| 4   | 등록 → 가맹점 생성/연결 → 목록·상세·CS 리포트 노출 흐름 | 매핑 전체 경로                          |

## 발견 사항과 조치

### 1. 자동완성 쿼리가 실전 검증이 없는 문법을 쓰고 있었음 — 교체 (원인 유력)

- 자동완성은 인입내역 목록 검색에서 복사한 **따옴표 감싼 ilike 패턴**
  (`business_name.ilike."%검색어%"`)을 사용했다.
- 그런데 그 목록 검색은 062(`deleted_at`) 미적용으로 **목록 자체가 만들어진 이후 줄곧
  0건으로 깨져 있어서, 이 문법이 운영에서 단 한 번도 실행된 적이 없었다.**
- 반면 가맹점 360 검색(`merchants/page.tsx`의 `applySearch`)은 매일 쓰이며 검증된
  방식이다 — `.or()` 문법 문자(쉼표·괄호·따옴표·백슬래시 등)를 검색어에서 **제거**하고
  따옴표 없는 `%검색어%` 패턴을 쓴다.
- 자동완성 쿼리가 실패해도 빈 결과로 조용히 삼켜져서(에러 미표시) "입력해도 아무것도
  안 뜸"이라는 증상만 남았다.

**조치**

- 자동완성·목록 검색 모두 가맹점 360과 동일한 방식으로 교체 (문법 문자 제거 + 비인용 패턴)
- 자동완성 쿼리 실패 시 `console.error`로 남기도록 변경 (조용한 삼킴 제거)

### 2. 이름을 똑같이 입력해도 제안을 클릭하지 않으면 새 가맹점이 생김 — 자동 재사용 추가

- 기존 동작: 자동완성 제안을 **클릭해야만** 기존 가맹점에 연결되고, 클릭 없이 그냥
  등록하면 상호명이 같아도 무조건 새 가맹점을 만들었다. "이름 입력해도 매핑 안 됨"의
  절반은 이 UX 문제.

**조치** — 등록 시 연결된 가맹점이 없으면 **동일 상호명(공백 제거 후 정확 일치) 가맹점을
먼저 찾아 재사용**하고, 없을 때만 새로 만든다. 동명 가맹점이 여러 개면 가장 최근 것을
쓴다.

### 3. 롤백 가드 보강

- 등록 실패 시 가맹점을 되돌리는 롤백이 "연결 안 함 = 새로 만듦"을 전제했는데,
  2번(동일 상호명 재사용)이 생기면서 기존 가맹점을 지우려 시도할 수 있는 경로가 생겼다.
- **이번 등록에서 실제로 새로 만든 경우에만** 롤백하도록 플래그(`createdMerchant`)로 교체.
- 참고: merchants에는 RLS DELETE 정책이 없어 클라이언트 롤백 삭제는 어차피 무시된다
  (실패 시 고아 가맹점이 남는 기존 한계 — 아래 남은 리스크 참고).

### 4. 매핑 전체 경로 점검 — 이상 없음

- 등록 → `tickets.merchant_id` 저장 → 목록/상세의 merchants 조인 표시: 정상
- 연결된 가맹점의 VAN 정보 → CS 리포트 토스계열/KICC 분류: 정상 (VAN 미상 인입 건은
  토스계열에만 합산되는 설계)
- 가맹점 360 검색·표시: 정상 (검증 기준으로 삼음)

## 오늘 함께 확인된 배경 문제 (별건, 이미 조치)

| 문제                      | 원인                                                             | 조치                                         |
| ------------------------- | ---------------------------------------------------------------- | -------------------------------------------- |
| 등록해도 목록이 항상 0건  | 운영 DB에 062(`deleted_at`) 미적용 → 목록 쿼리 42703             | 062 실행 안내 + 컬럼 없으면 필터만 빼는 폴백 |
| 등록 실패 + 가맹점만 생성 | `reception_channel`/`progress_note` 컬럼이 마이그레이션에 없었음 | 125 작성 + 없는 컬럼만 빼고 재시도           |
| 옛 "가맹 설치" 27건 노출  | 7월에 삭제된 자동 생성 코드의 잔재가 목록 복구로 드러남          | 정리 SQL 안내 (신규 생성 없음)               |

## 남은 리스크 / 확인 방법

1. **운영 DB에 다른 마이그레이션도 빠져 있을 수 있다.** 062가 빠져 있었다는 것은 순차
   적용이 안 됐다는 뜻. 화면별로 하나씩 터지기 전에 라이브 스키마와 `supabase/` 전체를
   대조하는 점검을 권장.
2. **동일 상호명 자동 재사용의 한계** — 상호명이 완전히 같아야 매핑된다. "와플캠퍼스"와
   "와플캠퍼스 강남점"은 다른 가맹점으로 취급 (의도된 동작). 애매하면 자동완성 제안을
   클릭해 명시적으로 연결하는 것이 정확하다.
3. **등록 실패 시 고아 가맹점** — merchants RLS에 DELETE 정책이 없어 클라이언트 롤백이
   무시된다. 등록 실패가 잦아지면 DELETE 정책 추가 또는 서버 액션 롤백으로 전환 검토.
4. **배포 시차** — 수정 확인은 Vercel 배포 완료(Ready) 후에. 자동완성이 여전히 안 되면
   브라우저 개발자도구 콘솔에 이제 "가맹점 검색 실패: ..." 메시지가 남으니 그 내용 공유.

## 재현 테스트 절차

1. 새 인입내역 → 상호명에 기존 가맹점 이름 일부 입력 → 300ms 후 제안 목록 표시 확인
2. 제안 클릭 → 파란 "연결됨" 카드 확인 → 등록 → 가맹점 360에 새 가맹점이 **안** 생겼는지 확인
3. 제안 클릭 없이 기존 상호명을 그대로 입력하고 등록 → 마찬가지로 새 가맹점이 없어야 함
4. 완전히 새로운 상호명으로 등록 → 가맹점 360에 1건 생성 확인
