# KICC 대응 · VAN사 구분과 CS 리포트 결정사항

## 2026-08-27

KICC와 신규 계약하면서 기존 코세스 계열 건과 갈라 보고, 매달 KICC에 제출할 CS 운영
보고서를 뽑기 위한 작업. 화면 흐름은 [flow.md](./flow.md) 참고.

---

## 배경

포스모스는 가맹점에 토스프론트를 설치하고 결제는 VAN사를 통해 처리한다. 지금까지 VAN은
코세스 계열(코세스1·코세스2·코벤·기가맹)뿐이었고, 여기에 KICC가 추가됐다.

KICC 요구는 단순히 가맹점을 관리하는 것이 아니라 **매달 운영 실적을 숫자로 제출**하는 것이다.

```
관리 가맹점 · 총 CS · 원격 해결률 · 출장 건수
전월 대비 장애 증감 · 반복 장애 상위 5종 · 교체 필요 장비 · 개선 필요 브랜드
```

## 왜 사이드바를 사업부로 나누지 않았나

초기 검토에서 `토스사업부` / `KICC사업부`로 메뉴를 가르는 안이 나왔으나 채택하지 않았다.

- 나눌 수 없는 자원이 너무 많다 — 기사, 창고·재고, 캘린더, 승인함은 계약사와 무관하게 공용이다.
  가맹점 대장도 한 가맹점이 양쪽에 걸릴 수 있다.
- **같은 CS 담당자가 양쪽을 다 처리한다.** 사업부로 가르면 하루에도 몇 번씩 메뉴를 오가야 한다.
- 가맹접수 하나를 나누자고 나머지 메뉴를 통째로 복사하는 셈이 된다.

대신 **화면은 그대로 두고 계열 필터**를 붙였다. 나중에 담당자가 완전히 갈리면 그때 사업부로
승격하면 되고, 반대 방향(사업부 → 필터)은 되돌리기가 훨씬 어렵다.

## 계열 판정 기준

`van_company`는 `"코세스2,코벤"`처럼 **쉼표로 여러 개**가 들어갈 수 있다(가맹접수 폼의
`VanMultiSelect`가 그렇게 저장한다). 그래서 목록 전체를 비교하지 않고 **KICC 포함 여부**로만
가른다.

| 계열     | 판정                                 |
| -------- | ------------------------------------ |
| KICC     | `van_company`에 `KICC`가 포함됨      |
| 토스계열 | 값이 있고 `KICC`가 없음              |
| 전체     | 조건 없음 — 값이 비어 있는 건도 포함 |

판정 로직이 화면마다 흩어지면 나중에 갈라지므로, 목록 배지는 공용 컴포넌트
`src/components/ui/VanBadge.tsx` 하나로 모았다. 색도 여기서 정한다 — 토스계열 파랑, KICC 초록.

## 화면마다 필터 방식이 다른 이유

세 화면에 같은 세그먼트를 넣었지만 **거르는 위치는 다르다.** 각 화면이 데이터를 가져오는
방식이 다르기 때문이다.

| 화면     | 거르는 곳 | 이유                                                                  |
| -------- | --------- | --------------------------------------------------------------------- |
| 가맹접수 | 화면      | 서버가 전체 행을 다 가져온다(아래 참고). 화면에서 걸러도 정확하다     |
| 가맹점   | 서버      | 50건씩 페이지네이션. 화면에서 거르면 현재 페이지 안에서만 걸린다      |
| 설치관리 | 서버      | 최근 300건만 가져온다. 화면에서 거르면 KICC 건이 0건으로 보일 수 있다 |

건수는 세 화면 모두 **필터와 같은 조건을 건 별도 count 쿼리**로 센다. 목록에 보이는 것만 세면
"300건 중 29건"이 전체 실적처럼 보여 오해를 산다.

## 가맹접수 목록의 1000행 상한

Supabase는 범위를 주지 않은 `select`에 **1000행 상한**을 건다. 가맹접수는 한 번에 다 가져오는
구조라 이 상한에 걸리면 그 뒤 건이 화면에서 조용히 사라진다. 과거 데이터 이관을 앞두고
`fetchAllApplications`로 1000건씩 끝까지 읽도록 바꿨다(상한 5000행, 도달 시 경고 로그).

같은 함정이 CS 리포트 집계와 알림 크론에도 있어 같은 방식으로 처리했다.

## 설치관리는 왜 컬럼을 추가하지 않았나

`installations`에는 `van_company`가 없다. 컬럼을 추가해 값을 복사하는 대신 **연결된
`franchise_applications`를 조인**해 읽는다.

- VAN사는 자주 바뀌는 값이 아니라 조인 비용이 문제되지 않는다.
- 값을 두 군데 두면 어긋났을 때 찾기가 훨씬 어렵다. 가맹접수에서 VAN사를 고치면 설치관리에도
  바로 반영되는 편이 낫다.
- 조인은 **필터가 걸렸을 때만 `!inner`**로 건다. 전체 조회에 `!inner`를 쓰면 가맹접수와 연결되지
  않은 설치건(직접 등록분)이 목록에서 사라진다.

## CS 지표를 왜 메모에 붙였나

`merchant_memo_entries`에는 이미 `entry_type`(as/claim/general/etc)과 AS 응대 체크리스트가
있었다. 하지만 체크리스트는 **"절차를 밟았다"**는 기록이지 **"결과가 무엇이었다"**가 아니다.

> `원격지원으로 해결 가능한지 확인했다` ✅ — 확인은 했다는 뜻이지, 원격으로 해결됐는지는 모른다.

그래서 보고서에 필요한 세 가지를 **고정 목록**으로 받는 컬럼을 더했다. 자유 텍스트로는 집계가
불가능하다.

| 컬럼             | 값                                            |
| ---------------- | --------------------------------------------- |
| `issue_category` | 결제 / 포스 / 장비 / 설치오류 / 사용법 / 기타 |
| `resolution`     | 전화 / 가이드 / 원격 / 출장 / 미해결          |
| `is_repeat`      | 처음 / 또 그럼                                |

새 테이블을 만들지 않은 이유 — CS 이력은 이미 메모에 쌓이고 있고, 별도 테이블을 만들면 같은
성격의 기록이 두 곳으로 갈라진다.

**기본값을 두지 않았다.** 자동으로 아무 값이나 들어가면 보고서가 거짓말이 된다. AS·클레임
유형일 때만 물어보고, 셋 다 고르지 않으면 저장되지 않는다. 미입력 건수는 리포트 상단에 경고로
띄운다.

## 원격 해결률의 분모

`REMOTE_RESOLUTIONS`(전화·가이드·원격) ÷ **`resolution`이 입력된 건**이다. 전체 건수로 나누지
않는다. 미입력 건을 분모에 넣으면 입력을 안 할수록 해결률이 떨어져 숫자가 실제와 멀어진다.

분모가 0이면 `0%`가 아니라 **`-`**로 표시한다. "아직 모름"과 "0%"는 다르다. 전월 대비 증감도
같은 이유로 전월이 0건이면 `-`다.

## 리포트가 틀린 숫자를 내보내지 않게

조회 자체가 실패했을 때 0으로 표시하면 "장애 0건"으로 오해해 그대로 KICC에 보고하게 된다.
그래서 두 가지를 뒀다.

- 조회 실패 시 빨간 배너 — "아래 수치는 실제 값이 아니니 보고에 사용하지 마세요"
- 실패했거나 스키마가 아직 적용되지 않은 상태에서는 **엑셀 내려받기 버튼 자체를 숨긴다**

## DB 변경 원칙

이번 작업의 스키마 변경은 **컬럼 추가와 인덱스 생성뿐**이다. `DROP COLUMN`·타입 변경·기존
데이터 `UPDATE`가 없다.

- `117_merchant_van_company_and_cs_metrics.sql` — `merchants.van_company`,
  `merchant_memo_entries`의 지표 3종. 모두 nullable
- `118_merchant_van_company_backfill.sql` — 가맹점 VAN사를 연결된 가맹접수에서 채움.
  `van_company IS NULL`인 행만 건드리므로 덮어쓸 값이 없다

`CHECK` 제약은 새 컬럼에만 걸었다. SQL에서 `NULL`은 CHECK를 통과하므로 기존 행이 걸리지 않는다.

마이그레이션이 적용되지 않은 환경에서도 화면이 500으로 죽지 않도록, 조회·저장 모두 컬럼 없음
에러(`42703`/`PGRST204`)를 잡아 신규 필드를 뺀 채 재시도한다.

## 미뤄둔 것

### 상태값 14개 → 7개

카드가맹·토스심사·인터넷 신청이 **거의 동시에** 일어나는데 상태는 한 줄로 늘어서 있다.
`card_internet_apply_done` 같은 합성 상태가 그 압력의 흔적이다.

7개(`서류대기`·`서류미비`·`접수완료`·`심사완료`·`완료`·`보류`·`취소`)로 줄이고 카드·토스를
별도 칸으로 빼는 안까지 정리했으나, 이번에는 하지 않았다.

- `card_done`만 코드에 318회 등장한다
- KPI가 상태 집합 4개에 직결돼 있어, 기준이 바뀌면 지난달과 이번달 숫자를 비교할 수 없게 된다.
  하필 이번 작업의 목적이 "전월 대비" 비교 보고서다
- 알림톡 템플릿이 상태별로 카카오에 등록돼 있어 상태를 합치면 **카카오 재승인**이 필요하다

KICC를 `van_company`로 넣기로 하면서 상태값을 먼저 정리할 이유가 사라졌다. 화면에 뜨는
`토스심사완료` 라벨만 `심사완료`로 바꿔(DB 값은 `toss_review_done` 그대로) 급한 불을 껐다.

### 알림톡 문구

고객에게 나가는 문구는 코드가 아니라 **카카오에 등록·승인된 템플릿**이다. `disableSms: true`라
문자 대체발송도 없으므로 코드 안의 문구는 실제로 나가지 않는다.

`토스 심사가 완료되었습니다`를 중립 문구로 바꾸려면 카카오 재승인(영업일 1~3일)이 필요해
별도로 신청했다. 승인 후 환경변수 `SOLAPI_KAKAO_TEMPLATE_FRANCHISEDONE` 값만 교체하면 된다.

같은 신청에서 **장비 선택 링크를 뺐다.** 고객이 고른 장비를 직원이 확인할 화면이 없어
반쪽짜리 기능이었고, 어차피 기술지원팀이 전화로 확인한다.

### 과거 데이터 이관

고객관리대장 CRM 2,038행을 가맹접수로 옮기는 작업을 준비해 1단계(1,872건)까지 실행했으나
되돌렸다. SQL은 `supabase/119`·`120`에 남아 있고 정리 규칙(VAN사 표기 통일, 상태 매핑,
날짜 물려받기, `import_batch` 도장)도 확정돼 있어 언제든 다시 실행할 수 있다.
