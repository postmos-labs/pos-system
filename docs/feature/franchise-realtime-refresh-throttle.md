# 가맹접수 실시간 재조회 제한

## 배경

- 가맹접수 화면은 `franchise_applications`의 모든 변경 이벤트마다 목록 전체를 다시 불러옴 (쿼리 30번 가까이, 1~2초)
- 일괄 상태 변경·일괄 이관·일괄 담당 지정처럼 건마다 저장하는 작업이나 동시 편집이 몰리면 재조회가 수십 번 이어져 5~10분씩 느려지는 것으로 보임 — 가설이며 측정으로 확인된 것은 아님
- 기존 디바운스 0.4초는 저장 간격이 0.4초보다 길면 거의 막아 주지 못함

## 결정

- 재조회는 화면당 10초에 최대 1번. 조용하다가 처음 온 변경은 0.4초 뒤 바로 반영하고, 이후 몰리는 변경은 모아서 한 번
- 내가 직접 고친 변경도 재조회 대상에서 빼지 않음
  - 처음에는 "이벤트로 온 행이 화면의 현재 행과 같으면 무시"하는 규칙을 넣었으나 뺐음
  - 이유: "오늘 완료" 건수·필터는 서버에서만 계산돼 내려오고(`todayCompletedIds`), 상태를 바꿔도 화면에서 따로 갱신하지 않음. 내가 고친 변경을 무시하면 "승인 완료"로 바꿔도 "오늘 완료"가 올라가지 않음
  - 이벤트에는 변경 전 값이 없어 "상태가 바뀐 변경인지"를 구분할 수 없어, 안전하게 모두 재조회 대상으로 둠

## 예상 효과

- 직원 5명이 화면을 열어 둔 상태에서 20건(건당 2초)을 일괄 처리하면 재조회 약 100번 → 약 25번 (가정에 따른 추정치, 약 75% 감소)

## 참고

- 다른 직원의 변경이 최대 10초 늦게 보일 수 있음
- 변경이 0.3초 간격처럼 아주 촘촘하게 몰리면 오히려 1번에서 2번으로 늘 수 있음 (처음 0.4초 뒤 1번, 10초 뒤 마무리 1번). 실제 일괄 저장은 건당 1~2초라 해당하지 않음
- `ChangesClient`·`InternetClient`·`TransfersClient`는 같은 패턴이지만 이번에 바꾸지 않음
- 효과 확인: 느렸던 시각의 Supabase 대시보드 CPU·연결 수, Vercel의 /franchise 처리 시간을 적용 전후로 비교
