# 인입내역 해결 절차 → 챗봇 학습 데이터

## 챗봇 데이터 화면 폐기 (2026-09-08)

사용자 결정: 챗봇 데이터는 인입내역에서만 관리한다. 별도 화면(`/chatbot-data`)과 메뉴, 그리고
JSON → 외부 LLM 정제 → 가져오기 파이프라인 UI를 지웠다. 세 번에 걸쳐 인입내역 기능을 다른 화면에
붙였다가 "없잖아"를 들은 끝의 결정이다. 데이터가 어디서 나오느냐가 기준이다.

남은 것은 인입내역 상단의 **CSV 다운로드** 하나다. 품질을 통과한 문의 내용·해결 절차를 두 열로
내려준다. 정제가 필요하면 그 CSV를 받아 밖에서 한다. 조회 함수(`fetchExportTargets`)는
`src/app/(app)/tickets/exportActions.ts`로 옮겼다.

`chatbot_training_data` 표와 그 데이터, 138번의 `chatbot_exported_at`·`source_ticket_ids` 컬럼은
그대로 둔다. 삭제는 되돌리기 어렵고, 화면은 git 이력에서 되살릴 수 있다. 위의 파이프라인 관련 절들은
이력으로 남긴다.

## 왜 만들었나

기술지원 인입내역에는 `resolution_steps`("해결 절차") 칸이 있다. 등록 화면에 "챗봇 학습에
사용됩니다"라고 안내까지 하면서 받고 있었지만, 정작 그 값을 읽어 가는 코드가 어디에도 없었다.
입력만 쌓이고 밖으로 나가는 경로가 없는 상태였다.

`chatbot_training_data` 테이블과 `/chatbot-data` 화면도 따로 있었지만, 손으로 등록하거나 과거
CS 기록 CSV를 이관해 넣는 용도였고 인입내역과는 연결이 없었다.

두 조각을 잇는다.

## 흐름

```
tickets.resolution_steps          (현장에서 급히 적은 원본)
        │  내보내기 — 상호·연락처 제외한 JSON
        ▼
   외부 LLM (DeepSeek)             정제 · 중복 병합 · 개인정보 제거
        │  가져오기 — 정제된 Q/A JSON
        ▼
chatbot_training_data             (챗봇이 쓸 학습셋)
```

정제 프롬프트에는 챗봇 관점 규칙이 세 개 더 있다(7~9번). 사장님이 직접 할 수 있는 조치만 남길 것,
데이터가 지워지는 조작은 원격 지원 요청으로 바꿀 것, 재발 표시가 있는 건은 신뢰도를 낮출 것.
검사기가 놓친 것을 잡는 마지막 그물이 정제 단계라서 여기도 같은 기준이어야 한다.

정제를 시스템 안에서 하지 않는 이유는 단순하다. 해결 절차는 응대 중에 급하게 적히기 때문에
문장 품질 편차가 크고, 같은 문제가 수십 건씩 중복되며, 주의 문구에도 불구하고 가맹점 이름이
섞여 들어온다. 이 정리는 LLM이 훨씬 잘한다. 시스템은 원본을 꺼내주고 결과를 받아 넣는
두 지점만 담당한다.

## 왜 내보냄 표시가 필요한가

두 번째 배치부터 문제가 된다. 이미 정제해 넣은 건을 구분할 수 없으면 매번 전체를 다시 LLM에
넣게 되고, 같은 절차가 학습셋에 중복으로 쌓인다.

`tickets.chatbot_exported_at`에 내보낸 시각을 찍고, 기본 대상은 이 값이 비어 있는 건으로 한다.
다시 받고 싶으면 모달의 "이미 내보낸 건도 포함"을 켠다.

표시는 파일을 내려받은 직후에 찍는다. 정제 결과를 되받는 시점에 찍는 방법도 있지만, LLM이
`source_ticket_ids`를 정확히 옮겨준다는 보장이 약해서 택하지 않았다.

## 개인정보

내보내기 파일에는 문의내용(`title`), 해결 절차(`resolution_steps`), 문제 유형, 반복 여부,
발생일만 담는다. 가맹점 상호와 연락처는 컬럼째 제외한다 — 이 파일이 외부 API로 나가기 때문이다.

절차 본문에 상호나 번호가 섞여 있는 경우까지는 코드가 막지 못한다. 정제 프롬프트의 4번 규칙이
그 부분을 담당한다.

## 파일

| 파일                                                 | 역할                                            |
| ---------------------------------------------------- | ----------------------------------------------- |
| `supabase/138_tickets_chatbot_export.sql`            | `chatbot_exported_at`, `source_ticket_ids` 추가 |
| `src/app/(app)/chatbot-data/actions.ts`              | 대상 조회 · 내보냄 표시 · 정제 결과 등록        |
| `src/app/(app)/chatbot-data/ChatbotExportImport.tsx` | 내보내기/가져오기 모달, 정제 프롬프트 템플릿    |
| `src/lib/resolutionQuality.ts`                       | 해결 절차 품질 판정 규칙                        |

`actions.ts`는 `service_role` 키를 쓰므로 RLS가 걸리지 않는다. 로그인 여부를 코드에서 직접
확인한다. `chatbot_training_data`의 기존 RLS가 authenticated면 읽기·쓰기를 허용하고 있어
권한 축을 새로 만들지 않고 같은 수준(로그인)으로 맞췄다.

## 마이그레이션 미적용 상태

138번이 아직 안 돌았어도 화면은 죽지 않는다.

- 내보내기 — `chatbot_exported_at` 필터가 42703을 내면 필터 없이 다시 조회하고, 이미 내보낸
  건을 구분할 수 없다는 안내를 화면에 띄운다.
- 내보냄 표시 — 컬럼이 없으면 실패로 보지 않고, 파일은 받았지만 표시는 못 남겼다고 알린다.
- 가져오기 — `source_ticket_ids`가 없으면 그 필드만 빼고 등록한다. 학습 데이터 자체는 들어간다.

## 내보내기 전 품질 점검

해결 절차는 응대 중에 급히 적힌다. 그대로 내보내면 정제 비용과 학습셋 품질이 같이 나빠지므로,
거르는 지점을 내보내기 직전에 두었다. 규칙은 `src/lib/resolutionQuality.ts`에 있다.

처음 규칙은 글의 모양만 봤다(길이, 줄바꿈, 개인정보, 응대 행동). 챗봇 관점에서 다시 보니
모자랐다. 챗봇은 사장님이 친 문장으로 비슷한 문제를 **찾고**, 찾은 절차를 사장님에게 **그대로
말한다**. 규칙은 이 두 용도에서 나와야 한다.

| 대상      | 코드                  | 판정                                                                  | 챗봇 관점 이유                              |
| --------- | --------------------- | --------------------------------------------------------------------- | ------------------------------------------- |
| 문의 내용 | `title_no_subject`    | 대상어(포스·카드 등)와 증상어(안 됨·방법 등)가 둘 다 있음             | 검색 열쇠. "포스 오류"는 다 걸림            |
| 문의 내용 | `title_personal_info` | 전화·상호·대표자명 없음                                               |                                             |
| 해결 절차 | `too_few_steps`       | `>` 줄바꿈 번호로 나뉜 단계 2개 이상                                  | 답변이 순서여야                             |
| 해결 절차 | `too_short`           | 25자 이상                                                             | `[a] > [b]` 껍데기 방지                     |
| 해결 절차 | `remote_access`       | `"원격"` 없음 (`"원격 지원 요청/안내/접수"`는 제외)                   | 직원이 대신 한 일은 사장님이 못 따라 함     |
| 해결 절차 | `staff_system`        | `전산`(전산 장애 제외)·`토스 파트너스` 없음                           | 밴 전산·KOCES·토스 파트너스는 직원만 들어감 |
| 해결 절차 | `dangerous`           | 초기화·포맷·재설치·데이터 삭제 없음 (temp·캐시·로그 정리 단계는 제외) | 매출 데이터가 날아가면 챗봇 탓              |
| 해결 절차 | `our_action`          | 유선·통화·콜백, ~드림·해드 없음                                       | 다른 가맹점에도 통해야                      |
| 해결 절차 | `personal_info`       | 전화·사업자·카드·계좌번호, 상호, 대표자명 없음                        | 외부로 나가는 파일이므로                    |

단계 구분자는 작성 예시대로 `>`가 기본이지만 줄바꿈과 번호 줄도 인정한다. 예전에 잘 적힌 건이
새 규칙에 걸리면 안 되기 때문이다. 양쪽에 공백이 있는 " - "도 단계로 본다.

**관리자 모드·마스터 비밀번호는 잡지 않고 원격 접속만 잡는다.** 처음에는 셋을 묶어 직원 전용
조치로 봤다. 사용자가 갈랐다. 관리자 모드와 마스터 비밀번호는 사장님이 직접 쓸 수 있는 것이라
절차에 있어도 된다. 원격 접속은 직원이 대신 한 일이라 사장님이 따라 할 수 없다. 원본에 남은 원격
조치를 사장님용 표현으로 바꾸는 일은 정제 프롬프트 7번이 맡는다.

**"안내"는 응대 행동으로 잡지 않는다.** 작성 예시 6의 "배달앱 고객센터로 안내"가 정당한 마지막
단계다. 규칙 하나가 정답 예시를 걸러내면 사람들이 검사기를 안 믿는다. 같은 이유로 `삭제`는
"데이터·전체·모두"가 앞에 붙을 때만 위험으로 본다 — "[메뉴삭제]"는 정상 사용법이다.

단계 수 최소는 2다. 3으로 하면 "재부팅 > 소액 승인 테스트" 같은 완벽한 두 단계 답변에 사람들이
"대기"를 끼워 넣는다.

규칙은 예시 7개(작성 예시 6개 + 번호 줄 형식 1개)와 잘못 적은 예 6개로 검증했다. 절차가 비어
있으면 판정하지 않는다 — 안 적은 것과 잘못 적은 것은 다르다.

**대괄호 규칙은 뺐다 (2026-09-08).** 실제 인입내역 108건을 내보내 보니 통과가 1건이었다. 107건이
"버튼명 없음"이었는데, 대괄호를 쓴 건이 첫 행 하나뿐이라 규칙이 판별력을 잃은 상태였다. 이대로
수정 요청을 돌리면 전부에 "대괄호로 적어주세요"가 나가 현장이 검사기를 무시하게 된다. 같은 점검에서
"1. 원격"처럼 한 단어로 적힌 원격 단계 13건이 원격 규칙에 안 걸렸고, 밴 전산·KOCES 전산·토스 파트너스
단계 9건이 아무 규칙에도 안 걸렸다. 원격 규칙을 넓히고 직원 전산 규칙을 새로 넣었다. 대시로 나눈
절차 3건이 "단계 없음"으로 잡혀 구분자에 " - "를 더했고, 연동·명의·선불권·스와이프 등 사전에 없던
말을 채웠다.

## 규칙은 마스터가 돌릴 때만 적용한다

처음에는 등록·수정 화면에서 실시간 체크리스트를 띄우고 미달이면 저장을 막으려 했다. 사용자가
막았다. 응대 중 급하게 적는 직원을 붙잡고 싶지 않다는 판단이다.

그래서 규칙이 적용되는 지점은 둘뿐이다.

- 챗봇 데이터 내보내기 모달 — 미달 건을 보여주고 기본으로 제외
- 인입내역 목록 — 마스터가 "품질 점검"을 켰을 때만 배지가 보이고 일괄 수정 요청이 가능

점검 모드는 브라우저에 남겨 페이지를 넘겨도 유지된다. 마스터가 아니면 품질 관련 UI가 아예
렌더되지 않는다. 평소 목록은 품질과 무관하게 깨끗해야 한다.

## 규칙이 못 하는 것

절차가 실제로 맞는지는 못 본다. 형식이 완벽한 틀린 절차가 형식이 엉망인 맞는 절차보다 챗봇에
해롭다 — 자신 있게 틀리기 때문이다. 지금 신호는 `is_repeat`(또 그럼) 하나이고 정제 프롬프트
9번 규칙이 이를 쓴다. 그 이상은 정제 결과를 사람이 검토하는 게이트가 있어야 하는데 아직 없다.
`chatbot_training_data`에 초안/승인 상태를 두는 것이 다음 단계다.

검색 문장이 하나뿐인 것, 화면에 뜬 오류 메시지를 안 받는 것, 포스 모델 정보가 없는 것도
규칙 밖의 문제다. 1차 데이터가 쌓인 뒤 다룬다.

## 발송은 자동으로 하지 않는다

규칙에는 오탐이 있다. 잘못 걸린 건이 자동으로 알림까지 나가면 직원이 수정 요청 자체를 무시하기
시작한다. 그래서 검사 결과로 본문만 미리 채워두고, 보내는 건 사람이 누른다. 기존
`requestTicketRevision`(tickets/actions.ts)을 그대로 쓴다 — 알림 발송과 기록이 이미 거기 있다.

보낼 수 없는 경우를 화면에서 먼저 걸러낸다.

- 이미 열린 수정 요청이 있으면 "요청 대기 중"으로 바꿔 중복을 막는다
- 담당자(sales/cs/tech)가 아무도 없으면 보낼 대상이 없으므로 "담당자 없음"
- 담당자가 보내는 본인뿐이면 화면에는 버튼이 뜨지만 서버가 거부한다. 조용히 실패하지 않고
  이유가 토스트로 뜬다

권한은 양쪽이 같다. 버튼은 마스터에게만 보이고 `requestTicketRevision`도 `requireMaster`로 막는다.

## 미달 건 제외

기본으로 켜 둔다. 제외된 건은 `chatbot_exported_at`을 찍지 않으므로 다음 배치에 다시 올라온다.
담당자가 고치면 자연히 통과해 대상에 들어온다.

`personal_info` 판정에 상호가 필요해 조회 컬럼에 `business_name`을 넣었지만, 반환되는 `rows`에는
담지 않는다. 내보내기 파일에서 상호·연락처를 뺀다는 원칙은 그대로다.

139번 마이그레이션이 아직 안 돌았으면 열린 요청을 알 수 없다. 조회 실패를 전체 실패로 만들지 않고
안내 문구만 띄운 뒤 전부 "없음"으로 둔다.

## 인입내역 목록에서도 보이게

처음에는 점검과 발송이 챗봇 데이터 화면에만 있었다. 그런데 해결 절차를 적는 사람도, 고쳐야 할
사람도 하루 종일 인입내역에 있다. 미달 사실을 알려면 다른 화면으로 건너가야 하는 구조였다.

인입내역 목록 행에 `해결 절차 미달 N` 배지를 띄우고, 체크박스로 여러 건을 골라 한 번에 수정
요청을 보낼 수 있게 했다. 이미 요청이 나가 있는 건은 `수정 요청 대기`로 따로 표시해 중복 선택을
막는다. 해결 절차가 비어 있는 건은 미달로 잡지 않는다 — 아직 안 적은 것과 잘못 적은 것은 다르다.

## 일괄 발송이 본문을 넘겨받지 않는 이유

`requestTicketRevisionsBulk`는 티켓 id 배열만 받는다. 본문은 서버가 각 건을 다시 읽고 다시
검사해 만든다. 화면이 만든 문장을 그대로 저장하면, 마스터 권한만 통과하면 임의의 내용을 담당자
알림으로 보낼 수 있게 된다. 검사 결과에서 나온 문장만 나가야 한다.

한 번에 200건으로 제한한다. 그 이상은 실수로 전체 선택한 경우다.

30일 지난 건은 보내지 않는다. 석 달 전 건을 기억으로 다시 적으면 지어낸 절차가 된다. 오래된
미달 건은 그냥 둔다 — 내보내기에서는 빠지므로 챗봇에 흘러가지 않고, 손실은 엉터리로 적힌 건에
한정된다. 단건 수정 요청(티켓 상세)에는 이 창을 두지 않는다. 사람이 내용을 보고 보내는 것이라
판단을 맡긴다.

건너뛴 건은 사유별로 세어 돌려준다 — 담당자 없음, 이미 요청 중, 미달 아님. 화면은 이 숫자를
토스트에 그대로 붙인다. 건수만 알려주면 왜 빠졌는지 알 수 없다.

목록은 담당자 유무를 모르므로 담당자 없는 미달 건도 화면에서는 대상에 포함된다. 서버가 걸러내고
사유를 돌려주므로 조용히 사라지지는 않는다.

## 담당자가 자기 수정 요청을 보는 자리

수정 요청은 알림으로 가지만, 알림은 닫으면 끝이다. 담당자가 나중에 "내가 고쳐야 할 게 뭐였지"를
찾을 자리가 없었다. 티켓 상세에 들어가야 배너가 보이고, `/tickets/revisions`는 마스터만 본다.

인입내역 목록 맨 위에 "나에게 온 수정 요청" 칸을 둔다. 내가 담당자(sales/cs/tech)인 건 중 대기
중인 요청을 요청 본문과 함께 보여주고, 제목을 누르면 상세로 간다. 없으면 칸 자체가 안 뜬다.

조회는 열린 요청 전체를 받아 서버에서 거른다. 대기 건은 마스터가 닫을 때마다 줄어 총량이 작고,
조인 컬럼에 or 필터를 거는 것보다 단순하다. 139번 마이그레이션이 없는 환경에서는 빈 칸으로 둔다.

## 수정 요청 관리에서 고쳤는지 보기

수정 요청을 보낸 뒤 마스터가 닫으려면 건마다 열어봐야 했다. 대기 목록에 표시 둘을 붙인다.

- **수정 여부.** `tickets.updated_at`이 요청 시각보다 뒤면 "수정됨 시각", 아니면 "아직 안 고침".
  `updated_at`은 001번 트리거가 수정할 때마다 갱신하므로 따로 기록할 게 없다.
- **지금 품질.** 현재 문의 내용과 해결 절차에 규칙을 다시 돌린다. 통과 / 미달(사유) / 절차 없음.
  절차가 비어 있으면 규칙이 []를 돌려주므로 "통과"로 보이면 안 된다. 따로 "절차 없음"으로 가른다.

"수정됨 + 통과"는 열지 않고 닫고, "수정됨 + 미달"은 다시 보내고, "아직 안 고침"은 기다린다.

## 고쳐서 통과하면 자동 완료 (2026-09-08)

담당자가 고쳐도 요청은 대기로 남고 마스터가 확인 완료를 눌러야 완료가 됐다. 사용자는 고친 건이
완료 탭에 바로 보이길 원했다. 상세 화면에서 문의 내용이나 해결 절차를 저장하면 서버가 지금 내용에
규칙을 다시 돌리고, 통과하면 대기 요청을 "고쳐서 품질 점검 통과 (자동 완료)"로 닫는다
(`autoResolveTicketRevision`). 판정은 서버가 하므로 담당자가 불러도 통과할 때만 닫힌다. 미달이면
대기로 남고 사유가 해결 절차 칸 아래에 뜬다. 마스터의 확인 완료 버튼은 미달인데도 받아주고 싶을 때
쓰는 예외 경로로 남긴다.

같은 날 상세 화면에 문의 내용 칸을 넣었다. 그동안 제목은 등록 뒤에 고칠 수 없어서 "문의 내용
불명확·개인정보" 지적을 받은 담당자가 할 수 있는 게 없었다.

전체 검토를 돌릴 때도 같은 일을 한다. 대기 중 요청 가운데 지금 통과하는 건을 먼저 완료로 닫고 나서
미달 건을 모은다(`resolvePassingTicketRevisions`). 자동 완료가 들어가기 전에 고쳐진 건이 대기에
남아 있었고, 마스터가 상세창에서 하나씩 확인 완료를 누르는 건 검토 버튼을 만든 취지와 맞지 않았다.

## 수정 요청 취소

잘못 보냈거나 담당자가 바뀐 요청을 거둬들일 방법이 없었다. 행을 지우면 보냈다는 기록이 사라지고,
완료로 닫으면 실제로 고친 것과 구분이 안 된다. 상태 `canceled`를 더한다(`supabase/142`).

취소하면 담당자에게 `ticket_revision_canceled` 알림이 간다. 이미 팝업을 봤을 수 있으니 고치지
않아도 된다고 알려야 한다. 인입내역의 "나에게 온 수정 요청" 칸은 대기 건만 보여주므로 취소된 건은
자연히 빠진다. 취소된 건은 대기가 아니므로 일괄 수정 요청에서 같은 건을 다시 보낼 수 있다.

일괄 수정 요청이 있으니 일괄 취소도 있어야 한다. 두 자리에 둔다. 관리 화면 대기 탭에서는 요청을
골라 사유와 함께 취소하고, 인입내역 목록에서는 일괄 발송한 그 자리에서 티켓을 골라 되돌린다(사유 없이).
목록의 "수정 요청 대기" 배지는 품질이 아니라 요청 상태이므로 품질 점검을 켜지 않아도 마스터에게
보인다. 대기 요청 조회도 미달 건이 아니라 페이지의 티켓 전부로 넓혔다 — 고쳐서 통과했지만 아직
안 닫힌 건도 목록에서 취소할 수 있어야 한다. 사유 하나가 전체에 들어가고 알림은 담당자마다 간다. 이미 처리된 건은 건너뛰고 건수로 알린다.

142가 아직 안 돌았으면 취소 버튼은 보이되 누르면 마이그레이션이 필요하다는 안내가 뜬다. 상태 CHECK
위반(23514)이나 컬럼 없음(42703)을 그 신호로 본다.

## 인입내역 한 자리에서 전부 (2026-09-08)

페이지가 50건씩이라 미달 건에 수정 요청을 보내려면 페이지마다 "미달 모두 선택 → 수정 요청"을
반복해야 했고, 보낸 요청이 고쳐졌는지는 사이드바의 관리 화면으로 가야 보였다. 사용자는 인입내역
탭을 벗어나지 않고 처리하고 싶어 한다. 마스터 전용 버튼 세 개를 인입내역에 둔다.

- **전체 검토** — 해결 절차가 있는 전체 건을 판정해 미달 건 담당자에게 한 번에 보낸다. 판정과
  대기 중 요청 여부는 CSV 내보내기 조회(`fetchExportTargets`)를 그대로 쓰고, 발송은 기존 일괄
  발송을 200건씩 나눠 부른다. 서버 액션을 새로 만들지 않은 이유다. 30일 지난 건은 서버가 걸러
  건수로 알린다.
- **수정 요청 전체 취소** — 페이지가 아니라 대기 중인 요청 전부를 거둔다. 판정 규칙이 바뀌어
  예전 기준으로 나간 요청을 한 번에 정리할 때 쓴다. 기록과 알림은 기존 일괄 취소가 맡는다.
- **수정 요청 내역** — 상세창에서 대기·완료·취소 탭으로 보고, 대기 건은 "수정됨 / 아직 안 고침"과
  "지금 통과 / 미달"을 확인한 뒤 바로 확인 완료를 누른다. 목록 조립은 관리 화면과 같은 함수
  (`revisionRows.ts`)를 쓰므로 두 화면의 판정이 어긋나지 않는다. 사유를 적거나 취소하려면 관리
  화면으로 간다.

**변경 전 → 변경 후 (2026-09-09).** 요청을 보낼 때 그 시점의 문의 내용과 해결 절차를
`before_title`·`before_steps`(`supabase/146`)에 같이 남긴다. 관리 화면과 인입내역의 수정 요청
내역에서 "변경 내용 보기"를 누르면 요청 당시 값과 지금 값을 줄 단위로 비교해 보여준다. 146 전에
보낸 요청은 스냅샷이 없어 "변경 전 기록 없음"으로 뜬다. 컬럼이 아직 없으면 스냅샷 없이 요청만
저장한다. 마스터가 확인 완료하면(전체 검토의 자동 완료 포함) 담당자에게
`ticket_revision_resolved` 알림이 간다 — 고친 사람이 닫혔는지 알 방법이 없었다.

## CSV 사본

문제상황/해결절차 두 열짜리 CSV를 두 곳에서 받을 수 있다. 챗봇 데이터 목록은 정제된
문제상황·해결방법을, 인입내역 내보내기 모달은 품질을 통과한 원본의 문의 내용·해결 절차를 내려준다.
챗봇 도구가 CSV를 받거나 엑셀로 훑어보는 용도다.

내보내기 모달의 CSV는 **내보냄 표시를 찍지 않는다.** 정제 파이프라인(JSON → LLM → 가져오기)과
달리 사본일 뿐이라, 찍으면 다음 배치에서 빠져 정제되지 않은 채 묻힌다. CSV를 챗봇의 진짜 입력으로
쓰기로 정하면 그때 표시를 찍는 쪽으로 바꾼다.

유틸은 `src/lib/csv.ts`. UTF-8 BOM과 CRLF를 붙여 엑셀에서 한글이 깨지지 않게 한다. `=`나 `@`로
시작하는 셀은 앞에 따옴표를 붙여 수식으로 해석되지 않게 한다. `-`와 `+`는 "- 재부팅" 같은 정상
목록이 흔해 건드리지 않는다.

## 챗봇 쪽은 RAG로

내보내기 형식을 파인튜닝용 대화 포맷이 아니라 Q/A 쌍으로 잡은 이유다. 이 규모(수백~수천 건)에서
파인튜닝은 비용 대비 효과가 없고, 절차가 바뀔 때마다 재학습해야 한다. `problem_situation`을
임베딩해 검색하고 `solution`을 근거로 답하는 쪽이 맞다.
