# 성능 점검 (2026-09-14)

"전체적으로 렉이 있는지" 확인 요청으로 운영 Vercel 통계와 코드를 같이 봤다. 결론과 결정 사항을 남긴다.

## 측정

운영(Vercel Observability, 최근 12시간, 함수 P75 처리 시간):

| 라우트                                                     | 호출 | P75    |
| ---------------------------------------------------------- | ---- | ------ |
| /franchise                                                 | 656  | 764ms  |
| /approvals                                                 | 757  | 451ms  |
| 그 외 (/installs, /dashboard, /tickets, /calendar, /woo …) | -    | 6~24ms |

브라우저(한국, 실제 화면 로드 완료까지): /approvals 0.9~~2.1초(첫 진입 5.6초), /dashboard 1.1초, /franchise 2.2초.
한국에서 로그인 화면 첫 바이트: 170~~590ms.

## 원인

1. **서버·DB가 시드니에 있다.** Supabase 프로젝트가 ap-southeast-2이고, `vercel.json`의 `regions: ["syd1"]`은
   DB 옆에 함수를 두려고 일부러 고정한 것(커밋 30f5bf5). 사용자는 한국이라 화면 하나 열 때, 표에서 칸 하나
   고칠 때마다 한국↔시드니 왕복(약 130~150ms)이 든다. 코드로는 못 줄이는 거리 비용이다.
2. **가맹접수는 625건 전부를 조인까지 붙여 매번 가져온다.** 설치·인터넷·통화 이력을 150개씩 나눠 30번 가까이
   묻는다. 건수가 늘수록 더 느려진다.
3. **인증 왕복이 요청마다 여러 번.** 미들웨어·레이아웃·페이지가 각각 `auth.getUser()`를 부른다. 운영 로그에서
   auth/v1/user 호출이 230~460ms로 외부 호출 중 가장 느렸다.
4. 승인함의 세 조회는 이미 병렬이다. 느린 건 3번과 거리 때문이다.

## 결정

- **DB 서울 이전은 보류.** 근본 해결이지만 백업·복원·중단이 따르는 이전 작업이라 시기를 따로 정한다.
  옮길 때는 Supabase 프로젝트를 ap-northeast-2로 만들고 `vercel.json`의 리전을 `icn1`로 같이 바꾼다.
  둘 중 하나만 옮기면 지금보다 나빠진다.
- **가맹접수 기본 조회를 줄인다.** 진행 중 건 + 최근 30일 안에 갱신된 완료·취소 건만 기본으로 가져오고,
  그 이전 완료·취소 건은 표 위 안내 줄의 "이전 건 모두 불러오기"로 가져온다(`fetchFranchiseListData`의
  `scope`, `loadArchivedFranchiseRows`). 알림·하이라이트로 들어온 건은 오래된 건이라도 `includeIds`로 같이
  가져온다. 검색·엑셀은 불러온 범위만 본다는 것을 안내 줄에 적었다.
- **인증·프로필 조회를 요청당 한 번으로.** `src/lib/auth/session.ts`의 `getSessionUser`·`getSessionProfile`
  (React `cache`)을 레이아웃과 주요 페이지가 같이 쓴다. 서버 액션은 요청 단위가 달라 캐시가 안 걸리므로
  기존대로 직접 검사한다.

## 손대지 않은 것

- 60초 알림 폴링, 캘린더·KPI의 제한 없는 조회 — 표가 작아 영향이 없다.
- 설치관리 3600줄·가맹접수 3400줄 클라이언트 — 렌더 자체는 20ms대라 지금은 문제가 아니다.
