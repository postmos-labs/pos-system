# 설치관리 오픈일 신호 (D-5 / D-3)

## 왜 만들었나

기술지원팀 발표자료 "오픈일정 누락방지 개선안"을 반영한 것이다.

설치관리 목록은 접수 상태·담당기사·장비·비고까지 다 보여주지만 **"언제까지"가 없다.** 그래서
담당자가 목록을 봐도 어느 가맹점을 먼저 챙겨야 하는지 판단할 수가 없다. 접수 이후에 오픈일이나
장비 구성이 바뀌어도 개별로 물어봐야 알고, 미처리 업무가 오픈 직전에 발견되면 설치 지연·장비
누락·결제 사고로 이어진다.

## 조사에서 나온 것 — 이미 있던 절반

착수 전에 훑어보니 발표자료가 요구하는 것 중 상당수가 이미 돌고 있었다.

| 항목             | 현황                                                       |
| ---------------- | ---------------------------------------------------------- |
| 오픈 예정일 컬럼 | `franchise_applications.open_date` (007번 마이그레이션)    |
| 접수 시 입력     | 가맹접수 등록·상세·접수증 화면에 모두 입력칸 있음          |
| 캘린더 표시      | `오픈` / `오픈예정일` 이벤트로 이미 렌더링                 |
| 오픈 D-day 알림  | `api/cron/franchise-alerts`가 D-7/D-3/D-1 알림을 매일 발송 |

빠진 건 기술지원팀 쪽이었다. 설치관리 화면에는 오픈일이 아예 안 보였고, 기존 알림의 수신자는
`cs_id`(CS)와 `sales_id`(영업)뿐이라 현장에 나가는 담당기사에게는 아무것도 가지 않았다.

그래서 새로 만든 것은 세 가지다 — 확정 오픈일 컬럼, 목록의 오픈일 신호, 기술지원용 알림.

## 데이터 — 예정일은 복사하지 않는다

`supabase/141_installations_open_date.sql`

```sql
ALTER TABLE installations ADD COLUMN IF NOT EXISTS open_date DATE;
```

새로 만든 건 **확정 오픈일** 하나뿐이다. 오픈 예정일은 가맹접수에서 조인해서 읽고 설치건에
복사하지 않는다.

```
installations.open_date          있으면 이 값이 기준        ← 설치관리에서 확정
        ?? franchise_applications.open_date                  ← 접수 시 입력한 예정일
```

복사하지 않는 이유는 정본이 갈라지기 때문이다. 접수 담당이 예정일을 고쳤을 때 설치관리 쪽 사본이
그대로 남으면 두 화면이 다른 날짜를 말하게 되고, 어느 쪽이 맞는지 알 방법이 없다. 조인해서 읽으면
접수에서 바꾼 값이 설치관리에 바로 반영된다.

가맹접수를 거치지 않고 직접 등록한 설치건(AS·배송·직접 등록)은 예정일이 없으므로 설치관리에서
`open_date`에 직접 입력한다.

목록 쿼리가 이미 `select("*")`라서, 마이그레이션을 실행하기 전에도 화면은 죽지 않고 오픈일 칸이
비어 보인다.

## 판정 — `src/lib/openSchedule.ts`

```
D-6 이상    표시만 (회색)
D-5 ~ D-4   노란색 · 필수 통화
D-3 ~ D-1   빨간색 · 최종 점검
D-DAY       파란색 · 오픈
지난 날짜    회색
완료·반려    신호 없음
```

**구간으로 해석한 이유.** 발표자료 문구는 "D-5 노란색 / D-3 빨간색"이지만, 그 두 날짜에만 색을
켜면 D-4와 D-2에는 신호가 꺼진다. 하루 건너뛰고 다시 켜지는 표시는 담당자가 신뢰하지 않게 되고,
그날 목록을 못 본 사람은 통화 대상인 줄도 모르고 지나간다. 켜진 뒤로는 오픈까지 계속 켜져 있어야
"누락 방지"가 성립한다.

**완료·반려 건은 항상 끈다.** 끝난 건에 빨간불이 남아 있으면 빨간색이 "확인 필요"를 뜻하지 않게
되고, 그 순간 신호 체계 전체가 무의미해진다.

## 화면 — 색은 행이 아니라 칩에

설치관리 표의 행 배경은 이미 두 가지가 쓰고 있다.

- 승인 대기 건 — 빨간 배경 + 깜빡임 (`animate-pulse bg-red-50`)
- 내가 담당인 건 — 노란 배경 (`bg-yellow-100`)

여기에 오픈 D-3 빨강과 D-5 노랑을 행 배경으로 또 얹으면 네 가지가 같은 두 색을 나눠 쓰게 되어
무엇을 뜻하는 빨강인지 구분할 수 없다. 그래서 오픈 신호는 **`오픈일` 열 안의 칩에만** 칠한다.
발표자료도 "색상 적용"이라고만 했지 행 전체라고 하지는 않았다.

넣은 곳:

- 목록 표 — `구분` 열 다음에 `오픈일` 열. 날짜 + `D-5` / `D-3` 칩
- 필터 칩 — `오픈 임박 N` (D-5 이내만 추림). 기존 `승인 대기` 칩 옆
- 상세 드로어 — 헤더에 오픈 칩, `일정·담당`에 오픈일 입력칸
- 모바일 카드 — 헤더 배지 옆에 칩

`scheduled_date`(설치 예정일)와 `open_date`(오픈일)는 다른 개념이다. 설치가 오픈보다 며칠 앞서는
경우가 흔해서 한 필드로 합칠 수 없다.

## 알림 — 기존 cron에 얹었다

`src/app/api/cron/franchise-alerts/route.ts`에 설치건 블록을 추가했다. 새 cron을 만들지 않은 이유는
같은 시각에 같은 성격의 일을 하기 때문이다 — 스케줄이 하나면 실행 실패도 한 곳만 보면 된다.

- 대상: 오픈일 D-5 / D-3인 미완료 설치건 (확정 오픈일 우선, 없으면 접수 예정일)
- 수신자: 담당기사 + 기술지원 팀장·실장 (담당기사가 비어 있어도 팀장은 배정을 챙겨야 한다)
- 중복 방지: 기존 `notification_logs` 패턴 (`entity_type: install_open_dday_notify`)
- 한 건이면 `installation_id`를 채워 눌렀을 때 `/installs?id=...`로 바로 이동

## 하지 않은 것

- 캘린더 — 오픈/오픈예정일 이벤트가 이미 있어서 손대지 않았다
- 고객 알림톡 — 내부 알림만. 오픈 임박은 우리 쪽 준비 상태지 고객에게 보낼 내용이 아니다
- 우국상·인터넷 화면 — 각자 별도의 `open_date`를 쓰고 있고 이번 흐름과 무관하다
